# Milestone M6: Final Benchmarks and Scalability Analysis

## 1. Status: Complete (measured, on this machine)

Hardware: NVIDIA GeForce RTX 4050 Laptop GPU (sm_89, 6GB VRAM, driver 581.80, CUDA runtime 13.0),
16.4GB system RAM. CUDA Toolkit 13.5 + MSVC (VS2022 Community). All numbers below are measured
(`scripts/run_m6_final_benchmarks.py`), not estimated — 2 warm-up runs discarded, 10 timed
repetitions per (subset, implementation), CUDA-event timing for GPU stages, wall-clock
`CPULocalOutlierFactor.timings_` for CPU stages.

**Data provenance note:** `data/raw/` holds no real CICIDS2017 CSVs on this machine. The processed
dataset (`data/processed/cicids2017_clean_full.npz`, 1,000,000 rows) and all stratified subsets were
generated by `preprocessing/prepare_dataset.py` from a synthetic CICIDS2017-shaped placeholder
(`synthetic_cicids2017.csv`, per `data/processed/dataset_metadata.json`). This does not affect the
timing/memory scalability conclusions below, which depend only on row count (N) and feature count
(D=68) — not on whether feature values are real or synthetic. It does mean "full dataset" here is
1,000,000 rows, not the 2,520,798-row figure quoted elsewhere in this repo for the real CICIDS2017
run on different hardware.

## 2. Memory feasibility (M6.1–M6.2)

Live check at run time: 5.78GB free VRAM, 4.03GB available system RAM (of 16.4GB total). A dense
N×N float32 distance matrix costs `4·N²` bytes — both the naive and M5-optimized CUDA kernels, and
the CPU matrix-expansion reference, all materialize this matrix in full.

| Subset | N | Distance matrix | CPU feasible | GPU feasible |
| :--- | ---: | ---: | :---: | :---: |
| 10k | 10,000 | 0.373 GB | ✅ | ✅ |
| 25k | 25,000 | 2.328 GB | ✅ | ✅ |
| 100k | 100,000 | 37.25 GB | ❌ | ❌ |
| 250k | 250,000 | 232.8 GB | ❌ | ❌ |
| 500k | 500,000 | 931.3 GB | ❌ | ❌ |
| 1m | 1,000,000 | 3725.3 GB | ❌ | ❌ |

100k and above are skipped — not run, not estimated — because 37GB+ exceeds both the available RAM
and free VRAM on this machine by a wide margin. Full detail in `results/m6_final_benchmarks/memory_analysis.csv`.

## 5. Scalability analysis (M6.4)

Runtime for every implementation grows quadratically with N, matching the O(N²) distance/k-NN
stages (reachability/LRD/LOF-scoring stay O(N·k) and negligible at every size tested — confirmed
in M4/M5). The practical ceiling on this hardware is not compute time but **memory**: the dense
N×N matrix crosses the ~5GB usable-VRAM line somewhere between N=25,000 (2.3GB, fits) and
N=100,000 (37GB, does not) — a 16× increase in N causes a 256× increase in matrix size, so there
is no intermediate dataset size in this project's prepared subsets that sits inside that gap.

Reaching 100K–1M-scale (or the real 2.52M-row CICIDS2017 dataset) requires a genuinely different
kernel architecture: a tiled/chunked/out-of-core pairwise-distance and k-NN computation that
processes the matrix in VRAM-sized blocks and only ever keeps the running top-k per row, never
allocating the full N×N matrix at once. M5's shared-memory tiling improved cache reuse *within* an
already-VRAM-resident matrix — it did not remove the matrix's existence. Out-of-core chunking is
well-scoped future work, not implemented here.

## 7. What M6 does not claim

- No benchmark above 25,000 rows was executed. The `100k`/`250k`/`500k`/`1m` rows in
  `memory_analysis.csv` are feasibility estimates, not timing results.
- Peak memory figures are approximate (sampling methodology is stated per-row in the CSV), not
  exact high-water-mark instrumentation.
- `src/python/benchmarking/milestones.py`'s own M4–M6 projections remain in the repo as a
  pre-CUDA-toolkit historical artifact; they are superseded for 10k/25k by this milestone's real
  measurements but kept for comparison, per the measured-vs-projected chart.
